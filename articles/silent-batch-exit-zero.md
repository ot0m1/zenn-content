GMOペパボでホスティングサービスの運用と開発をしている akimotos です。マネージドクラウドの月次請求バッチで起きた「1件だけ請求が消える」障害を調べていたら、staging 環境の同じバッチが1年半前から一度も仕事をしていないのに、毎月「成功」と記録され続けていたことが分かりました。この記事では、なぜ失敗が成功に見えていたのか、どこで検知できたはずだったのかを、再現手順と一緒にまとめます。

## 起きたこと

きっかけは CS からのエスカレーションでした。あるお客様の7月分の請求だけが存在しない。前月分はあり、翌月分も正常に作られている。バッチのログを見ると、いつもどおりのサマリが1行あるだけでした。

```
$ env NODE_ENV=production yarn run cli ./jobs/payments/bulk-fix-bill-amounts.ts 2026 7
{ total: 9202, affected: 9067, error: 135 }
Done in 27326.73s.
```

error が 135 件。ただしこの数字は毎月 130 件前後で、内訳は「決済 NG で停止中のプロジェクト」です。そこに想定外の失敗が1件混ざっても、数字の上では区別がつきません。cron は標準出力だけをファイルに残し、標準エラー出力は捨てていたので、例外のスタックトレースはどこにも残っていませんでした。

## 直接の原因: 7時間半のバッチと、その間のカード差し替え

このバッチは開始時に全プロジェクト（約 9,200 件）をメモリに読み込み、1件ずつ請求レコードを作っていきます。所要時間は 7 時間半です。

問題のプロジェクトでは、バッチ実行中にお客様がクレジットカードを差し替えていました。バッチが持っているのは開始時点のインスタンスなので、payment_id は旧カードのままです。請求レコードの作成はプロジェクトのステータス更新と同一トランザクションで行われ、プロジェクトの保存時には ORM のフック（`@BeforeValidate`）で「カードの所有者が正しいか」を検証します。この検証が旧 payment_id でカードを検索し、行が無いので例外になり、トランザクションごとロールバックされました。結果として請求レコードは作られず、後段の決済バッチも確定メールも「対象なし」として素通りしました。

ローカル環境（Node 14 + PostgreSQL 14、外部 API はスタブ）で「カードを削除した状態のプロジェクトに対してバッチを実行」すると、本番と同じ状態（`SequelizeEmptyResultError` で失敗、請求レコード無し、ステータスは ok のまま）を再現できました。

恒久対応は、この検証の発火条件を「新規作成時と payment_id / user_id の変更時」に限定することです。既存のテスト 338 件が通ること、同じ状況で請求が正常に作られることをローカルで確認しています。

ここまでは年に1件程度の稀な競合の話です。本題は、この調査の途中で見つかったもう一つの問題です。

## 本題: 初期化に失敗したジョブが終了コード 0 で終わる

ジョブの共通エントリポイントは、おおよそ次の形をしていました。

```ts
// misc/index.ts（簡略化）
export async function execute(job: Job) {
  await job.init();      // 環境変数のチェックなど
  await job.run();
}

// 呼び出し側
execute(job).catch((e) => {
  notifySlack(e);
  process.exit(1);
});
```

一見すると失敗は catch で拾われ、Slack に通知され、終了コード 1 で終わるように見えます。ところが実際の呼び出し経路では、`init()` の中で必須環境変数が無いときに throw する箇所が、`.catch()` が張られるより前に評価される作りになっていました。Node 14 では、誰にも捕捉されない Promise の reject は `UnhandledPromiseRejectionWarning` を標準エラーに出すだけで、プロセスは終了コード 0 で終わります（Node 15 以降は既定で終了コード 1 になります）。

つまり、

- 標準エラー出力は cron が捨てている
- 終了コードは 0
- Slack 通知は catch の中にあるので呼ばれない

の三つが揃い、cron からも Slack からも「成功」にしか見えません。

## staging は1年半、何もしていなかった

この経路で実際に死んでいたのが staging の月次ジョブでした。

2025年3月に本番へ必須環境変数が3つ追加されました（決済ゲートウェイの OAuth エンドポイント、API エンドポイント、3D セキュア用のシークレット）。staging のジョブサーバーの `.env` にはこれが反映されず、以後すべてのジョブが起動直後に初期化で失敗し、終了コード 0 で終わっていました。staging の請求レコードは 2025年3月分を最後に、1年半にわたって一度も作られていません。その間、cron のログには毎月「Done」が並び、誰も疑いませんでした。

`.env` に3つを追記して手動実行すると、`{ total: 3390, affected: 157, error: 3233 }` と、正常にジョブが回りました（staging には決済 NG のダミーデータが大量にあるので error が多いのは想定どおりです）。

本番でも、必須環境変数が1つ欠けた瞬間に同じ経路で全件が黙って飛びます。「staging だから実害がなかった」のではなく、「本番でまだ起きていないだけ」でした。

## 何が検知器の外にあったのか

振り返ると、監視や通知は存在していました。cron のログはあり、Slack 通知もあり、error 件数のサマリも出ていた。それでも1年半気づけなかったのは、検知器が測っている対象と、知りたい事象がずれていたからです。

| 知りたいこと | 実際に測っていたもの | ずれ |
|---|---|---|
| ジョブが仕事をしたか | プロセスの終了コード | 初期化失敗が 0 を返す |
| 想定外の失敗が起きたか | error の合計件数 | 想定内の 130 件に埋もれる |
| 例外の中身 | 標準出力 | 標準エラーは捨てていた |
| 失敗が人に届いたか | Slack 通知の有無 | 通知コードに到達しない経路がある |

「エラーが上がっていない」は「正常」の根拠にはなりません。エラーを上げる装置に到達しない失敗経路がある限り、沈黙は成功と区別できないからです。

## 対策

1. **初期化失敗を終了コード 1 で終わらせる。** `process.on('unhandledRejection', ...)` で明示的に終了させるか、エントリポイントの呼び出しを try/catch で包む。Node のバージョンを上げれば既定挙動で 1 になりますが、バージョン依存に頼らずコードで固定します。
2. **失敗を「想定内」と「想定外」に分けて通知する。** 決済 NG で作成不可の件数と、それ以外の例外を別々に集計し、後者が 1 件でもあれば Slack に例外の内容ごと出す。合計件数だけの通知は、想定内のノイズが想定外を隠します。
3. **cron の標準エラー出力を残す。** `2>&1` でログに落とすだけで、今回の調査の半分は不要でした。
4. **「仕事をした」を直接測る。** 終了コードではなく、成果物（今回なら当月分の請求レコード数）を月次で数えて前月と比較する。0 件なら異常、というだけの監視で staging の1年半は初月に見つかっていました。

1 と 2 は PR 化済みで、staging で次の月次実行を通してから本番に入れます。3 と 4 は順次進めます。

## まとめ

- 長時間バッチは、開始時点のスナップショットで走る。その間に変わりうるデータ（今回は支払い手段）を検証に使うなら、検証のタイミングを絞るか、直前に読み直す
- 「失敗したら通知する」コードは、失敗がそのコードに到達する経路を全部通るとは限らない。とくに初期化とプロセス終了まわりは、ランタイムの既定挙動（Node 14 の unhandled rejection）に足をすくわれる
- 監視は「エラーが出たか」でなく「仕事をしたか」を測る。成果物の件数を数えるのが一番安い
- 検知の仕組みが無い環境は、動いているように見えるまま死ぬ。staging で1年半、本番でも同じ構造が残っていた
